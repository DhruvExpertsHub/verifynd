# Rule catalogue

The mistakes verifynd looks for, in priority order. Each entry says what
the mistake looks like, what the safe version looks like, how a rule can
find it, and why it sits where it does. A glossary of every abbreviation
is at the end.

> **Status: planned.** No rule is written yet. The **Status** column will
> move to *Written* and then *Tested* as each rule lands with its test file.

## How this list was ranked

Every family was scored on three things:

1. **How often it appears in code like verifynd's target**: plain,
   procedural PHP with `mysqli`, written from tutorials, run on XAMPP.
2. **How badly and how often it is exploited** in real attacks.
3. **How reliably an Opengrep rule can catch it** by reading one file.

"Most reported" and "most exploited" are different lists. Cross-site
scripting is the most *reported* web weakness, while command injection,
code injection and unsafe deserialisation are the most *exploited*
([CWE Top 25, 2025][cwe25]; [CWE KEV list, 2025][cwekev]). So in verifynd:

- **Severity follows impact.** Anything that hands an attacker the server
  is `ERROR`, even if it is rare.
- **Build order follows cheapness and frequency.** Near-certain pattern
  rules come first, so every week ends with working, tested rules.

There is one honest gap in the evidence: no published study measures
security flaws in student PHP code directly. The closest stand-ins used
here are low-star GitHub projects built from flawed tutorials
([Unruh et al., 2017][unruh]), PHP sites generated by GPT-4
([Tóth et al., 2024][toth]), and CVEs filed against free "PHP project"
websites ([SourceCodester sample][sourcecodester]; [PHPGurukul sample][phpgurukul]).

## Three kinds of rule

| Kind | What it does | Analogy |
|---|---|---|
| **Pattern** | Finds a code shape, e.g. `or die(mysqli_error($conn))` | A word search |
| **Taint** | Follows visitor data from where it enters (`$_GET`, `$_POST`: the *source*) to a dangerous function (the *sink*), unless it passes a cleaning step on the way (the *sanitizer*, e.g. `intval`) | Dye dropped into water pipes: an alarm sounds if dyed water reaches the tap unfiltered |
| **Audit** | Flags a code smell that is often, not always, a bug, and asks a human to look | A smoke detector: worth a check, sometimes it is just toast |

Opengrep reads **one file at a time**. With `--taint-intrafile` it follows
data between functions inside that file, but not into files pulled in with
`include`/`require` ([Opengrep intrafile tainting][og-intrafile]). Every
entry below is rated with that limit in mind.

## Tier 1: the flaws that hand over the database or the server

### 1. SQL injection in `mysqli` queries · CWE-89

**Looks like**
```php
$sql = "SELECT * FROM users WHERE username='$u' AND password='$p'";
$res = mysqli_query($conn, $sql);
mysqli_query($conn, "DELETE FROM quiz WHERE id=" . $_GET['id']);
$stmt = $conn->prepare("SELECT * FROM t WHERE name = '$name'");   // prepare() misused
```
**Safe version:** a prepared statement with `?` placeholders and
`bind_param`. Fetch the user by name, then check the password with
`password_verify()`. Never put the password in the `WHERE` clause.

**How the rule finds it:** taint from `$_GET`, `$_POST`, `$_REQUEST`,
`$_COOKIE` and visitor-controlled `$_SERVER` keys into `mysqli_query`,
`mysqli_multi_query`, `mysqli_real_query`, `->query()`, `->multi_query()`,
and into the SQL text given to `prepare()` / `mysqli_prepare()`.
`intval`, `(int)`/`(float)` casts and `filter_var(..., FILTER_VALIDATE_INT)`
count as cleaning. A separate audit sub-rule flags
`mysqli_real_escape_string` used in an *unquoted* number position
(`WHERE id=$id`), where escaping does nothing.

**Why first:** about 80% of bugs found in tutorial-copied GitHub code
([Unruh et al.][unruh]); 91.1% of PHP files containing SQL build it by
joining strings ([Dennis et al., 2024][dennis]); 13 of a 30-CVE
SourceCodester sample ([sample][sourcecodester]); 8 of 10 PHPGurukul CVEs
([sample][phpgurukul]). The classic `admin' or 1=1-- -` login bypass was
tested on Windows and XAMPP ([Exploit-DB 50522][edb50522]).

**Gap filled:** the open Semgrep rule matches any string with SQL words in
it, not `mysqli_query`, and does not treat `intval` or casts as cleaning
([tainted-sql-string][sg-sqli]).

### 2. Cross-site scripting (XSS) in PHP output · CWE-79

**Looks like**
```php
echo "Results for " . $_GET['q'];
<?= $row['comment'] ?>                                   // stored, from the database
<form action="<?php echo $_SERVER['PHP_SELF']; ?>">      // reflected via the URL path
<input value='<?php echo htmlspecialchars($name); ?>'>   // single quotes not encoded
```
**Safe version:** `htmlspecialchars($x, ENT_QUOTES, 'UTF-8')` at the
moment of output. JSON endpoints send `Content-Type: application/json`
and use `json_encode`.

**How the rule finds it:** taint into `echo`, `print`, `printf` and
`<?= ?>`. Reflected XSS (from the request) is `ERROR`. Stored XSS (from
`mysqli_fetch_*` rows) is `WARNING`, because research tools raised more
false alarms than real ones here ([Al Kassar et al., 2022][alkassar]).
Files that send a JSON content type are not flagged.

**Why second:** the most reported web weakness of 2025
([CWE Top 25][cwe25]) and the top bug-bounty finding
([HackerOne][h1]). It ranks below SQL injection because each finding
usually does less damage. *To test by hand first:* whether Opengrep
treats `<?= $x ?>` like `echo $x;`.

### 3. Unrestricted file upload · CWE-434

**Looks like**
```php
move_uploaded_file($_FILES['f']['tmp_name'], "uploads/" . $_FILES['f']['name']);
if ($_FILES['f']['type'] == 'image/jpeg') { ... }   // the browser chooses this value
if ($ext != 'php') { ... }                          // .phtml, .php5, .pHp slip past
```
**Safe version:** allow a short list of lowercase extensions
(`in_array(strtolower($ext), ['jpg','png','pdf'], true)`), name the file
yourself (`bin2hex(random_bytes(16)) . '.jpg'`), store it outside the web
root, limit its size, and never trust the browser's file type
([OWASP File Upload Cheat Sheet][owasp-upload]).

**How the rule finds it:** (a) taint from `$_FILES[...]['name']` into
`move_uploaded_file`. `basename()` does **not** count as cleaning here,
because `shell.php` survives it. (b) A pattern for any check on
`$_FILES[...]['type']`. (c) An audit for `move_uploaded_file` with no
allow-list check in the same function.

**Why third:** one uploaded `shell.php` gives the attacker the server
([PortSwigger][ps-upload]). 78% of GPT-4 upload handlers checked no
extension ([Tóth et al.][toth]); file upload was 38% of 2024's
high-threat WordPress bugs ([Wordfence 2024][wordfence]).

**Gap filled:** no open Semgrep PHP rule mentions `move_uploaded_file`
([semgrep-rules PHP folder][sg-php]).

### 4. Missing login or role check · CWE-862, CWE-698

**Looks like**
```php
// admin/delete_user.php: no session check at all
mysqli_query($conn, "DELETE FROM users WHERE id=" . intval($_GET['id']));

if (!isset($_SESSION['role'])) { header("Location: ../login.php"); }   // no exit
```
**Safe version:** every protected page starts with one shared guard file
that checks the login **and** the role, then calls `header(...)` followed
by `exit;`. A redirect only *asks* the browser to leave; without `exit`
the page is still built and sent.

**How the rule finds it:** (a) a precise pattern for `header("Location...")`
not followed by `exit`/`die`. (b) An audit, limited to folders like
`admin/` and `teacher/`, for files that write to the database, delete or
upload with no `$_SESSION` check and no `require` of a guard-like file.
(b) is low–medium reliability, because the real check may live elsewhere.

**Why fourth, and why new:** broken access control is OWASP's #1 for 2025
([OWASP A01:2025][owasp-a01]), missing authorisation rose to #4 in the CWE
Top 25 ([CWE Top 25][cwe25]), and it was the most exploited WordPress
class of 2025 ([Patchstack][patchstack]).

### 5. SQL identifier injection · CWE-89

**Looks like:** `"SELECT * FROM results ORDER BY " . $_GET['sort']`

**Safe version:** look the column up in a fixed list:
`$cols = ['date' => 'created_at', 'score' => 'score']; $col = $cols[$_GET['sort']] ?? 'created_at';`

**How the rule finds it:** taint into the part of a SQL string that
follows `ORDER BY`, `GROUP BY`, `FROM`, `INTO` or `UPDATE`. A lookup in a
fixed array, `match` or `in_array(..., true)` counts as cleaning.

**Why it ranks this high:** prepared statements **cannot** fix it, so a
student who has learned them will believe the code is safe. 15 of 40
tested PHP apps were exploitable this way, and it made up 8.6% of 2022's
SQL injection CVEs ([Dennis et al.][dennis]).

### 6. `include` / `require` built from input · CWE-98

**Looks like:** `include($_GET['page'] . ".php");`

**Safe version:** `in_array($_GET['page'], ['home','about','quiz'], true)`
before including, with a default page otherwise.

**How the rule finds it:** taint into `include`, `include_once`,
`require`, `require_once`. `basename()` alone is not treated as enough.

**Why here:** the largest number of confirmed bugs in a study of 1,854
popular PHP projects: 100 of 455 inspected includes
([Backes et al., 2017][backes]).

### 7. Running code: `eval`, shell commands, `unserialize` · CWE-94, CWE-78, CWE-502

**Looks like:** `system("ping " . $_GET['host']);`, `` `ls $dir` ``,
`eval($_POST['code']);`, `unserialize($_COOKIE['prefs']);`

**Safe version:** avoid the call. If a shell call is unavoidable, wrap every
argument in `escapeshellarg()`. Store structured data with
`json_encode`/`json_decode`, which cannot create objects.

**How the rule finds it:** taint into `eval`, `assert`, `system`, `exec`,
`shell_exec`, `passthru`, `proc_open`, `popen`, backticks and
`unserialize`.

**Why here:** rare in student code, but these are the most *exploited*
classes: OS command injection is #1 by real-world exploitation
([CWE KEV list][cwekev]), and working `unserialize` exploits were
generated for 30 PHP apps with zero false positives
([FUGIO, 2022][fugio]).

## Tier 2: trusting the browser, and weak logins

### 8. Privilege from the browser · CWE-269, CWE-915

**Looks like:** `$_SESSION['role'] = $_POST['role'];`, an `INSERT` that
writes `$_POST['role']` into `users`, `extract($_POST);`

**Safe version:** the server sets the role (`learner` by default) and only
an admin-guarded page can change it. Read inputs one by one:
`$email = $_POST['email'] ?? '';`

**How the rule finds it:** a pattern for `extract()` on any superglobal
(very high reliability). Taint from the request into `$_SESSION` keys or
SQL columns named like `role`, `is_admin`, `user_type`, `level`
(medium–high).

**Why:** privilege escalation was 24% of 2024's high-threat WordPress
bugs ([Wordfence 2024][wordfence]). `extract()` also blinds other
analysers ([Al Kassar et al.][alkassar]).

### 9. IDOR: trusting `user_id` from the request · CWE-639

**Looks like:** `"... WHERE student_id = " . intval($_GET['student_id'])`.
`intval` stops SQL injection, **not** IDOR.

**Safe version:** take your own identity from `$_SESSION['user_id']`. For
other people's records, add an ownership condition such as
`AND teacher_id = ?`, bound to the session value.

**How the rule finds it:** an audit for request keys named `user_id`,
`uid`, `student_id`, `learner_id`, `teacher_id` reaching SQL in a file
that also reads `$_SESSION`.

**Why:** IDOR rose to #24 in the CWE Top 25 ([CWE Top 25][cwe25]) and led
Intigriti's 2024 findings ([Intigriti][intigriti]).

### 10. Weak password storage and loose comparison · CWE-328, CWE-916, CWE-697

**Looks like:** `md5($_POST['password'])`, `sha1($pass)`, a plain password
in an `INSERT`, `if ($_POST['password'] == $row['password'])`,
`strcmp(...) == 0`, `in_array($x, $list)` without `true`,
`... AND password='$p'`.

**Safe version:** `password_hash($pw, PASSWORD_DEFAULT)` to store,
`password_verify()` to check, `hash_equals()` for tokens, `===` elsewhere.

**How the rule finds it:** patterns limited to values named like `pass`,
`pwd`, `token`, `hash`, `otp`, so ordinary `md5()` cache keys are not
flagged.

**Why:** login code is always hand-written in student apps, and PHP's loose
`==` makes `md5('240610708') == md5('QNKCDZO')` true
([PayloadsAllTheThings][patt]). Honest caveat: no real-world exploitation
data was found for weak hashing.

### 11. Database errors and debug output shown to visitors · CWE-209, CWE-200

**Looks like:** `or die(mysqli_error($conn))`, `echo $sql . mysqli_error($conn);`,
`ini_set('display_errors', 1);`, `phpinfo();`

**Safe version:** `error_log(...)` on the server, a plain message for the
visitor, `display_errors` off on the live site.

**How the rule finds it:** patterns. Very high reliability: the best first
rule to build.

**Why:** a leaked SQL error turns a blind injection into one that prints
its own results. Security misconfiguration is OWASP's #2 for 2025
([Reflectiz summary][reflectiz]).

**Gap filled:** no open Semgrep PHP rule mentions `mysqli_error` or
`or die` ([semgrep-rules PHP folder][sg-php]).

### 12. File paths and URLs from input · CWE-22, CWE-918

**Looks like:** `readfile("files/" . $_GET['f'])`, `unlink("uploads/" . $_POST['name'])`,
`file_get_contents($_GET['url'])`

**Safe version:** look the file up by database ID, or use `basename()` plus
a `realpath()` prefix check; allow only known hosts for URLs.

**How the rule finds it:** taint into file-reading, file-deleting and
URL-fetching functions.

**Why:** path traversal is #6 in the CWE Top 25 with 82 entries in CISA's
exploited list ([CWE Top 25][cwe25]; [CISA KEV][kev]), though rare in
tutorial code.

### 13. Scores, prices and amounts decided by the browser · CWE-602

**Looks like:** `"INSERT INTO scores (user_id, score) VALUES (..., {$_POST['score']})"`

**Safe version:** the browser sends only the *answers*; the server looks up
the correct ones and computes the score.

**How the rule finds it:** an audit for request keys named like `score`,
`marks`, `grade`, `price`, `amount`, `total`, `discount` written to the
database.

**Why:** trusting browser-computed values is a well-documented research
problem ([NoTamper][notamper]), and for a quiz platform it means any
learner can award themselves full marks.

## Tier 3: cheap rules with weaker evidence

| # | Family | Looks like | Safe version | Notes |
|---|---|---|---|---|
| 14 | `innerHTML` from fetched data · CWE-79 | `el.innerHTML = data.question` | `textContent`, or build elements | Not covered by the research; kept because quiz pages that render fetched JSON are exactly this shape |
| 15 | Login without `session_regenerate_id(true)` · CWE-384 | A file that sets `$_SESSION['user_id']` but never regenerates the ID | Call `session_regenerate_id(true)` right after a successful login | Confirmed in only 1 of 158 cases in a large study ([Backes et al.][backes]), so ranked low |
| 16 | Open redirect · CWE-601 | `header("Location: " . $_GET['next'])` | Allow only relative paths that start with `/` and not `//` | Used in phishing; 1 entry in CISA's exploited list |
| 17 | Weak random tokens · CWE-338 | `$token = md5(uniqid())`, `rand()` for reset codes | `random_bytes()` / `random_int()` | Commercial tools have it; the open Semgrep set does not |
| 18 | Hard-coded DB login · CWE-798 | `mysqli_connect("localhost", "root", "", "app")` | Credentials in a git-ignored config file; a real password on the live server | `INFO`: fires on almost every XAMPP project; stronger message for `root` + blank |
| 19 | Legacy `mysql_*` functions · CWE-477 | `mysql_query(...)` | `mysqli` with prepared statements | `INFO`: removed in PHP 7, so a sign of copied outdated code |

## Manual checklist: what rules cannot see

Some problems are about something *missing* across the whole app, or about
what the app is *meant* to do. verifynd prints this checklist alongside
its findings, because a rule reading one file cannot judge them.

- [ ] **CSRF protection.** Do forms that change data carry a secret token
      the server checks? Are deletes done by plain links like
      `delete.php?id=5`? Plain PHP has no standard token name to look for,
      so a rule would be noisy.
- [ ] **Login attempt limit.** Does the login lock or slow down after
      repeated wrong passwords?
- [ ] **Answers and scoring stay on the server.** Does any response send
      correct answers to the browser, or does JavaScript compute the score?
- [ ] **Business rules.** Can a teacher see only their own learners? Can a
      locked quiz be retaken by calling the server directly? Who may issue
      a certificate?
- [ ] **Session and PHP settings, checked once.** Login cookie flags
      (`HttpOnly`, `Secure`, `SameSite`), `display_errors` off,
      `allow_url_include` off, `session_destroy()` on logout.
- [ ] **Security headers.** Content-Security-Policy, X-Frame-Options and
      similar, checked once with the browser's developer tools.
- [ ] **Deployment hygiene.** phpMyAdmin not public, no `root`/blank
      database login, no `debug.log`, `.sql` dumps or backups in the web
      root.
- [ ] **Cross-file confirmation.** Any finding that might be handled in
      another file (a guard in `auth.php`, a cleaning function in
      `functions.php`) needs a human to confirm.

## Build order

1. **Near-certain pattern rules:** #11 (error output), the
   redirect-without-`exit` part of #4, `extract()` from #8.
2. **The core taint rules:** #1 (SQL injection) and #3 (upload), with
   careful `ok:` test cases.
3. **XSS (#2)**, with the JSON and stored-data tuning.
4. **The rest of Tiers 1–2.**
5. **The audit heuristics (#4b, #9, #13)**, paired with the checklist.
6. **Tier 3.**

## How rules are tested and measured

- **Every rule ships with a test file** beside it. A `// ruleid:` comment
  marks a line that must be flagged; a `// ok:` comment marks a line that
  must not be ([Semgrep rule testing][sg-test]).
- **Recall** (the share of real bugs caught) will be measured on NIST's
  labelled PHP test suite of about 42,000 cases
  ([Stivalet & Fong, 2016][sard]).
- **Precision** (the share of alarms that are real) will be measured by
  checking findings by hand on real tutorial-style GitHub projects. Only
  totals are published, and serious problems are reported privately to
  the project's owner.

## Independence

verifynd's rules and tests are written from scratch. The open Semgrep rules
have been under the Semgrep Rules License v1.0 since December 2024, which
allows only internal, non-competing use ([Semgrep announcement][sg-licence]),
so verifynd does not copy their rules, tests or source and sink lists. The
public documentation cited here (CWE, OWASP, Psalm's docs, research papers)
is used for understanding only.

## Glossary

| Term | Meaning |
|---|---|
| CSRF | Cross-Site Request Forgery: another website makes your browser submit a form |
| CVE | Common Vulnerabilities and Exposures: public IDs for specific known bugs |
| CWE | Common Weakness Enumeration: a catalogue of weakness *types* (CWE-89 is SQL injection) |
| ERROR / WARNING / INFO | Severity levels a rule assigns to its findings |
| IDOR | Insecure Direct Object Reference: changing an ID in a request shows someone else's data |
| KEV | CISA's Known Exploited Vulnerabilities catalogue: bugs confirmed used in real attacks |
| CISA | US Cybersecurity and Infrastructure Security Agency |
| LFI / RFI | Local / Remote File Inclusion: `include` loads a file the attacker chose |
| mysqli | PHP's "MySQL improved" extension for talking to MySQL/MariaDB |
| NIST / SARD | US National Institute of Standards and Technology / its Software Assurance Reference Dataset of labelled test code |
| OWASP | Open Worldwide Application Security Project, publisher of the Top 10 and security cheat sheets |
| RCE | Remote Code Execution: an attacker runs their own code on your server |
| SQL | Structured Query Language, used to talk to the database |
| SSRF | Server-Side Request Forgery: tricking your server into fetching an address the attacker chose |
| XAMPP | A local bundle of Apache, MariaDB/MySQL, PHP and Perl |
| XSS | Cross-Site Scripting: attacker text runs as script in someone else's browser |
